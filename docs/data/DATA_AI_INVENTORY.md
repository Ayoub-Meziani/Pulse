### 1.2 ML training set (synthetic) [verified]
| | `readings.csv` | `daily_context.csv` |
|---|---|---|
| rows | 37,250 | 18,000 |
| patients | 200 (`patient_key` S0001–S0200) | 200 |
| period | 2026-01-01 → 2026-03-31 (90 days), tz Africa/Algiers | same, one row per patient-day |
| columns | `patient_key, measured_at, local_date, session (morning/evening), systolic, diastolic, pulse, is_synthetic, generator_version` | `patient_key, local_date, on_medication, missed_dose, activity_minutes, sodium_mg_estimated, sleep_hours, sleep_quality (1–5), is_synthetic` |
| per patient | 121–251 readings (median 185); 63–90 days with ≥1 reading (median 84) | 90 days |
| value ranges | SBP 62–198 (mean 139.4), DBP 51–175 (mean 86.8), pulse 50–97 | activity 0–60 min, sodium estimate 800–7000 mg |
| missing values | no empty cells; **missing data = missing rows** (skipped sessions, 5–45 % per patient) | `missed_dose` empty on 7,110 rows = patient not on medication (121 of 200 patients are on medication) |
| deliberate errors | 106 rows with systolic ≤ diastolic (simulated swapped entry, about 0.3 %). They are **not flagged** by any column and must be filtered by the same rule as DB policy `pulse-v1` | none |

**How the data is generated** (see `simulate.py` lines 79–81 and 294–297):
- Each patient's baseline systolic is drawn uniformly from 110–165. Diastolic is about 0.62 × systolic.
- Each patient has a small daily trend.
- Day-to-day variation follows an AR(1) latent effect, plus measurement noise.
- Morning readings are +4 mmHg (a "morning surge").
- Invented effects:
  - +6 mmHg the day after a missed dose
  - +1.2 mmHg per extra 1,000 mg of sodium
  - −2 mmHg on days with 30 or more minutes of activity
  - +2 mmHg on days with less than 6 h of sleep

**Limitations:**
- These effects are **invented**. A model trained on this set only learns the generator's formula.
- Metrics on this set say nothing about real patients.
- There are no symptoms, demographics, medication names or device metadata.
- Pulse is not linked to blood pressure.

## 4. Analytics and clinical logic

| component | where | status | deterministic or ML |
|---|---|---|---|
| Plausibility / data-quality policy `pulse-v1` | DB trigger `private.validate_measurement` | **working** [verified in catalog; tests reported] | deterministic |
| Alert rules | starter `rules.py` **removed** (team contract B1); the backend owns `api/app/analysis/rules.py` | nothing writes to `alerts` yet (0 rows) [verified] | deterministic |
| Trend summary | backend `api/app/analysis/summary.py` (7/30-day means, trend, % above target) | backend-owned; not part of this workstream | deterministic |
| Daily/weekly analytics, morning vs evening, coverage | – | **missing** | – |
| ML predictions | – | **missing** | – |

**Thresholds now in code:**
- **Severe:** systolic > 180 or diastolic > 120. This produces `severely_high`, which prompts a repeat reading after at least 1 minute.
- **Emergency symptoms:** chest_pain, shortness_of_breath, weakness, vision_change, difficulty_speaking. These produce `possible_emergency` regardless of blood pressure.
- **Above target:** above the clinician's `care_plans.target_systolic/diastolic`. The seed targets are 135/85.
- **Data plausibility (DB):**
  - Invalid: systolic ≤ diastolic; systolic outside 50–300; diastolic outside 25–200; pulse outside 25–250; reading more than 5 minutes in the future.
  - Needs review: systolic outside 70–250 or diastolic outside 40–150; estimated (non-cuff) value; identical repeat within 2 minutes.

**Sources:**
- The alert thresholds come from the team's conception report and the starter kit.
- The plausibility limits are engineering defaults.
- **No clinician has reviewed them, and there are no guideline citations** (e.g. ESH/ACC-AHA) in the code. This is a known gap.

**Resolved inconsistency:** the starter `rules.py` used different ranges (40–300 / 20–200) from DB policy `pulse-v1` (50–300 / 25–200). It has been removed. The DB trigger is the single source of truth (team contract).

## 7. Access requirements for integration

**Main PULSE repository:**
1. Repository URL and the name of the default branch.
2. Write access to a feature branch (e.g. `data-layer`), or the agreed fork/PR workflow, and who reviews PRs.
3. Where the data code should live: copy `supabase/` and `pulse_data/` into the main repo as-is, or keep a separate repo or submodule.
4. Whether the main repo already has a `supabase/` folder or migrations, which must be merged rather than overwritten.

**Supabase (team project):**
1. Project ref and region, and confirmation that this is the PULSE project (no other app's data in it).
2. A Supabase organisation member role allowed to run `supabase link` + `supabase db push` (Developer or higher), or a named teammate who applies our migrations.
3. A database connection string (pooler or direct), only for server-side tools such as the import CLI and future ML batch jobs. Share it out of band and keep it in a local `.env`, which is git-ignored.
4. Service-role key: backend/server secrets only (rule engine, imports, assignments). It must never reach the frontend, the repo or logs.
5. Anon/publishable key and project URL: for the frontend (safe to ship; RLS is the protection).
6. Agreement that `seed.sql` (demo users with a known password) is **never** pushed to the shared project. Demo data goes to a separate dev project or branch only.
7. Auth settings decision: email confirmation on or off for the demo, and how doctor and admin roles are assigned (service role / SQL by the project owner).

**People and decisions:**
- A clinician (or the team's medical adviser) to review the alert and plausibility thresholds and the emergency wording.
- A verified emergency number for Algeria.
- The device model, if any.
- A `HAWK_API_KEY` if the team wants a DAST scan.
